### 3.1 五个核心抽象（本周核心概念）

先用一张表建立全局印象，再逐个击破。**这五个职责是验收标准第 1 条的原文考点，必须能脱口而出**：

| 抽象              | 一句话职责                           | 输入 → 输出                | Java 类比                          |
| --------------- | -------------------------------- | ---------------------- | -------------------------------- |
| **Runnable**    | 一切能被 LCEL 编排的单元的基协议，不是某个具体类 | 任意 → 任意               | 函数式接口 `Function<I, O>`           |
| **ChatModel**   | 封装 LLM 调用，抹平各厂商请求/响应差异     | 消息列表 → `AIMessage`    | 你第 2 周写的 `LLMProvider` 具体实现      |
| **PromptTemplate** | 把变量渲染成消息模板，不手写字符串拼接     | `dict` → 消息列表          | `String.format` / 模板引擎             |
| **OutputParser** | 把模型的自由文本输出解析成结构化对象       | `str` → 结构化对象（dict/模型）  | Jackson 反序列化 + Bean Validation 校验 |
| **Retriever**   | 按查询召回相关文档（本周只认接口，不碰实现）   | 查询 `str` → `Document[]` | 搜索引擎 / DAO 查询接口                 |

逐个要点与易错点：

```python
# ① ChatModel：统一入口，切换模型只换构造参数，不动调用代码
from langchain.chat_models import init_chat_model   # 1.x 推荐：一个函数初始化所有厂商

# ② PromptTemplate：变量用 {} 占位，渲染后才是真正的消息
from langchain_core.prompts import ChatPromptTemplate
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是{system_name}的运维助手，只回答与该系统相关的问题。"),
    ("human", "{question}"),
])
# 易错点：模板里字面量出现的花括号（如 JSON 示例）要写成 {{ }} 转义

# ③ OutputParser：与第 2 周 Pydantic schema 对接，别重复造轮子
from langchain_core.output_parsers import JsonOutputParser
parser = JsonOutputParser(pydantic_object=TicketExtract)   # 复用第 2 周的 schema
# 易错点：Parser 只负责"解析 + 校验"，不保证模型一定输出合法 JSON；
#        失败重试仍走第 2 周写的"错误回灌 → 最多 3 次"逻辑

# ④ Retriever：本周只要会用接口 invoke(query)，向量库/切分是第 7~9 周的事
# docs = retriever.invoke("网关熔断怎么配置")  → list[Document]
# 易错点：别现在就扎进 Milvus/pgvector，本周认接口即可，否则严重拖进度

# ⑤ Runnable：不是实例化用的类，而是"上述一切组件共同遵守的协议"
# 任何组件只要实现 invoke/ainvoke/stream 等方法，就能被管道符 | 串起来
```

### 3.2 LCEL 与 Runnable 协议（关键原理）

**LCEL（LangChain Expression Language）** 是本周最值得花时间理解的原理，它解释了"为什么这些组件能像乐高一样拼起来"。

核心就三件事：

1. **统一调用协议**：每个 Runnable 都提供 `invoke`（同步）、`ainvoke`（异步）、`stream` / `astream`（流式）、`batch`（批量）。**同一段编排代码，换一个调用方法就能从同步切到异步/流式**——这正是你第 1 周攻 `asyncio` 的用武之地。
2. **管道符 `|` 的本质**：`a | b` 构造一个 `RunnableSequence`，把 a 的输出喂给 b 的输入。它不是语法糖，而是真的生成了一个新 Runnable。
3. **三种组合子**：串行 `|`（RunnableSequence）、并行 `RunnableParallel`（ branches 同时跑，输出 dict）、任意逻辑 `RunnableLambda`（把普通函数包成 Runnable）。

```python
# LCEL 标准写法：一条链 = PromptTemplate + ChatModel + OutputParser
chain = prompt | model | parser

# 同步 / 异步 / 流式，同一条链，换个方法即可
result = chain.invoke({"system_name": "cyclone", "question": "支付超时怎么排查"})
result = await chain.ainvoke({...})        # 异步：生产环境默认用这个
for token in model.stream(...):            # 流式：第 4 周展开，这里只知道有这个能力
    ...

# 并行组合：一次问两个模型，输出 {'qwen': ..., 'deepseek': ...}
from langchain_core.runnables import RunnableParallel
both = RunnableParallel(qwen=qwen_model, deepseek=deepseek_model)
```

**易错点**：`|` 两侧必须都是 Runnable；直接把字符串或 dict 塞进链会报错，需要用 `RunnableLambda` 包装。`ainvoke` 链上任何一环是同步阻塞的，异步优势就会失效——这一点在第 4 周做并发时会集中体现。

### 3.3 2026 版本现状与选型边界（易错点集中区）

> 🔴 **版本陷阱（很多人栽在这）**：2026 年 10 月 LangChain 已是 1.4.6 / LangGraph 1.2.16。当前推荐范式是：
>
> - **简单 Agent** → `create_agent`（harness 模式，快路径）
> - **复杂流程** → `StateGraph`（节点/边/条件路由/持久化/中断）
> - **不要用** `AgentExecutor`、旧的 `LLMChain`、旧的 memory 类
> - 面试时能说清"什么场景用 harness、什么场景上 graph"，是明显的加分项

**选型边界速查表**（`create_agent` vs `StateGraph`，本周只记边界，不展开实现）：

| 维度        | `create_agent`（harness 快路径） | `StateGraph`（状态图）            |
| --------- | ---------------------------- | ----------------------------- |
| 适用        | 单 Agent + 工具调用，线性决策         | 多节点/条件分支/循环/人工审批/需持久化      |
| 上手成本      | 低，几行代码可用                   | 高，要设计状态、节点、边                |
| 可控性       | 框架托管内部循环                   | 你自己掌控每一步流转                  |
| 对应你项目    | 简单问答机器人                     | RPA 流程编排（第 13~14 周展开）       |
| 本周动作      | **知道它存在、知道边界即可，不动手**     | 同左，动手留到第 14 周               |

**import 路径陷阱**（照着 2024 年的旧博客抄代码是本周最高频的翻车点）：

- **稳定契约层** → `langchain_core`：Runnable、PromptTemplate、OutputParser、回调等，**长期不变，优先从这里 import**。
- **高层封装** → `langchain`：`create_agent`、`init_chat_model` 等新范式入口。
- **社区集成** → `langchain_community`：第三方向量库/工具，变动频繁。
- 凡是教程里出现 `from langchain import LLMChain` / `AgentExecutor` / `ConversationBufferMemory`，**直接判定为过期内容，不要跟**。

### 3.4 从 LangChain 抽象回到 P1 网关（应掌握的实践技能）

**P1 · 多模型统一网关 v0.1 目标**（本周完成的部分）——这正是你 Java 侧做过的多模型适配器，用 Python + 第 3 周抽象重做一遍：

```python
# 统一 LLM 客户端抽象 —— 直接复用第 1 周的 Protocol 和第 2 周的三厂商适配器
from dataclasses import dataclass
from typing import Any, Protocol

@dataclass
class LLMResponse:
    """统一响应对象：内容、token 用量、耗时、成本估算"""
    content: str
    input_tokens: int
    output_tokens: int
    latency_ms: float
    cost_yuan: float

class LLMProvider(Protocol):
    async def chat(self, messages: list[Message], **opts: Any) -> LLMResponse: ...
    def supports_function_call(self) -> bool: ...
    def cost_per_1k_tokens(self) -> tuple[float, float]: ...  # (input, output)
```

- 实现 `QwenProvider` / `DeepSeekProvider` / `ZhipuProvider` 三个适配器 → **第 2 周已写好，本周纳入统一协议，不要重写**。
- 基于配置切换模型，带降级链（DeepSeek 挂了自动切 Qwen）→ 先写 `try/except` + 优先级列表的最小骨架；**熔断、健康检查、调用审计是第 5 周内容，本周不要提前挖坑**。
- 输出统一响应对象：内容、token 用量、耗时、成本估算 → 成本公式 `成本 = 输入token/1000 × 输入单价 + 输出token/1000 × 输出单价`，单价从配置读，**不要硬编码进代码**（厂商会调价）。

> 💡 **本周的"项目产出"标准**：不是写一个能跑的 Demo，而是搭出一个**结构清晰、下周能往上加东西**的骨架——目录分层（provider / config / model / tests）、统一协议、配置驱动、一条能打印成本的最小调用链。宁可功能少，也要接口干净。
