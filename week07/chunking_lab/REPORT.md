# 第 7 周切分实验报告

## 运行方式与环境

```bash
.venv/Scripts/python.exe -m week07.chunking_lab
```

语料：`SGCC-4012 网关运维知识库`，10 个标题；报告中的数字直接复制自上述命令的
终端输出（2026-11-26 实跑），未使用任何业务系统数据。

## 实测对比表

| 策略 | chunk 数 | 平均 token | 结构截断率 |
| --- | ---: | ---: | ---: |
| A 固定 512/64 | 3 | 392.0 | 33% |
| B 递归 512/64 | 3 | 390.0 | 0% |
| C 标题前缀 | 10 | 115.7 | 0% |
| D small-to-big（小块 96 / 父块 512） | 18 | 71.4 | 56% |

## 结果解读

1. **A 与 B 的 chunk 数接近，但截断率差别明显**：固定切分把条款或表格行从中间
   劈开，递归切分优先在自然边界断开。两者长度都远小于 512，说明断点质量
   与块数并不等价。
2. **C 的收益来自结构而非算法**：只是把标题路径拼进前缀，10 个 chunk 全部
   带有"属于哪一节"的信息，且结构截断率为 0。这是文档所说的"成本极低、
   效果通常优于固定长度"。
3. **D 的截断率反而最高**：小块 96 token 提高了检索粒度，但更容易把第 N 条
   或表格行切断。真实系统里应接受这个代价，并用父块上下文弥补——命中
   小块后返回 `metadata.parent_text`，而不是把小块原样塞进 Prompt。
4. **不能只看 chunk 数判定优劣**：D 的 18 块不是"切得更细所以更好"，
   要看父块是否被正确关联、是否按父块去重。

## 人工抽检建议

按 README 的四条提示，对每种策略各抽 10 个样本，重点看：

- `SGCC-4012` / `ERR_4012` 是否整块保留；
- 第 N 条是否以句末标点收尾；
- 表格行是否保持"故障码 → 处置建议"完整；
- 脱离原文后是否能从 chunk 自身判断所属章节。

## 结论（面试可用）

结构化文档优先按标题切分并加标题前缀；先修检索（解析保真 + 切分），
再谈重排与生成。本实验用零成本的结构信息把结构截断率从 33% 降到 0%，
验证了这一顺序判断。embedding 与向量检索的效果将在第 8 周继续验证。
