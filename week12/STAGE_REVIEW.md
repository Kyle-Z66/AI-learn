## 二、复盘模板四问（填写示例）

### 1. 本阶段我独立完成了什么？

- **能 run 的**：P2 RAG 服务（FastAPI + Docker + CLI 自检）；10 个评测机制样例 + 10 个生成机制样例；
  100 条教学 golden set 与四配置评测链。
- **有指标的**：四配置 Recall@5 / MRR@10 / Context Precision / Context Recall /
  Faithfulness / Answer Relevance / p95 延迟；逐案 recall 分布；CI 退出码。
- **能讲的**：引用编号为什么必须"先截断后分配"；低温度为什么不等于不幻觉；
  Recall 与 Precision 分母为什么不同；消融如何归因；CI 门禁为什么是护栏不是成绩单。

### 2. 哪些知识点我理解但用不出来？

- 真实向量库（pgvector / Milvus）的索引参数与召回调优，本地只用 TF-IDF 替身。
- 真实 Rerank 模型（cross-encoder）的延迟预算与批量推理；这里是确定性纯函数。
- NLI 模型做 Faithfulness 深度判定；目前只做数字/实体可核验声明的粗校验。
- LangChain/LangGraph 的 Agent 组合子还没在真实工具链上跑过（第 13 周开始）。

→ **下阶段找机会用**：第 13 周把"检索 + 生成 + 工具调用"接成可执行 Agent 流程，
并用本周 golden set 做回归基线。

### 3. 哪些我完全没搞懂？

- RRF 常数 60 在大规模候选下的最优取值，以及不同召回路数如何归一化。
- 业务侧标注规范的制定：谁来标、冲突怎么裁决、难例如何持续沉淀。
- 线上延迟受网络/批处理/缓存的影响程度（本地只有单机教学测量）。

→ **标记**：面试前重点补前两项的公开资料；第三项等拿到真实环境与 Key 再测。

## 三、面试自述（脱稿练习稿）

1. **先修检索再修生成**：同一套查询集下，四种检索配置的 Recall@5 在 0.900~0.950 之间、
   MRR@10 在 0.424~0.547 之间，而 Faithfulness 全部 1.000——说明"答案里的数字都在上下文里"
   并不能证明"上下文是对的"。所以生成质量上限由检索决定，必须先修检索。
2. **四配置消融**：BM25 单字切分召回宽但噪声大；TF-IDF 替身区分度更好；
   RRF 融合两条名次列表；rerank 在 Top10 内重排。真实结果显示 hybrid+rerank 的 Recall
   反而从 0.950 降到 0.900，因为重排用的实词覆盖率让短小的归档片段占优——
   这正是必须做消融而不是背结论的原因。
3. **生成侧可靠性**：引用在上下文组装阶段编号（先截断后编号），答案带 `[1][2]`，
   后处理映射回 doc_id/标题/页码；相关性预检挡无关检索，数字/实体后校验挡编造；
   低温度 0.1 与结构化输出降低随机性但不保证事实正确。
4. **评测集怎么来的**：本仓库是 100 条教学样例，metadata 明确标注来源与规则；
   真实替换要做领域标注、dev/holdout 划分、难例持续沉淀，不能造数据。
5. **CI 回归**：比较当前与基线，质量下降/延迟上升超容差即退出码 1；
   它是护栏不是成绩单，选型要看报告与分布。

## 四、短板与第 13 周 Agent 衔接边界

- 本周短板：真实向量/重排/NLI 组件均缺；golden set 是教学样例；p95 只是本地测量。
- 第 13 周起进入 Agent：本周的 `RAGService.query()` 将作为 Agent 的一个工具，
  评测集成为每次改动的回归基线；本周不实现工具调用、规划与记忆（第 13 周任务）。
- 衔接原则：Agent 的每一步仍要输出可观测状态（refused / guard_passed / 引用），
  否则第 11~12 周建立的可靠性与评测能力会在编排层丢失。
