# 从"跑通 RAG"到"能证明 RAG 有效"：一套可复算评测体系的落地

> 第 12 周技术输出。用途：面试时讲清"我做了什么、为什么这么做、和只会跑 Demo 的区别"。
> 叙事主线：**不是换模型，而是把 Java 侧的测试/灰度思维平移成 RAG 的可量化回归体系。**

## 1. 背景：跑通之后的问题

第 7~11 周把 RAG 链路搭起来了：解析、切分、召回、重排、带引用生成、拒答与幻觉抑制。
但一旦被问"这套系统到底好不好、比上一版好在哪"，只能回答"我感觉更准了"。
这在 Java 团队里等价于"接口能跑就上线"——没有单测、没有压测、没有回归门禁。

于是第 12 周的目标变成：**把主观感觉变成可复算的工程证据。**

| 周次 | 交付物 | 对应 Java 经验 |
| --- | --- | --- |
| 第 7 周 | 解析与切分实验 | 数据 ETL 与预处理管线 |
| 第 8~9 周 | 嵌入 / 索引 / BM25 混合召回 | 多数据源聚合与双路路由 |
| 第 10 周 | 重排与 Top-K 收敛 | 结果二次排序策略 |
| 第 11 周 | 引用 / 拒答 / 幻觉守卫 | 返回值校验与熔断式降级 |
| 第 12 周 | golden set / 指标 / 消融 / CI | 测试集 + 性能基准 + 回归门禁 |

## 2. 能力平移映射表（面试可直接讲）

| Java 侧概念 | Python 落地 | 关键差异 |
| --- | --- | --- |
| 测试数据集 + @Test | `golden_set.json` + pytest | 评测集是累加资产，用版本号与 case_id 管理 |
| JMeter 压测报告 | `runner.py` 四配置消融 | 一次跑完 4×100 次调用，表格由程序渲染 |
| 断言 / 回归测试 | `ci_gate.py` 阈值 + 退出码 | 质量下降与延迟上升方向相反，符号别写反 |
| Bean Validation | Pydantic `extra="forbid"` | 解析即校验，少一层 controller if |
| DTO / Map 传值 | frozen dataclass | 结果不可变，报告与门禁共用同一份 |
| CI Pipeline | `exit_code() 0/1` | 门禁只挡退化，不做配置排名 |

## 3. 架构与数据流

调用方 → FastAPI 边界校验 → RAGService（配置分流 + 计时）→ 四配置检索 →
复用第 11 周生成器 → 带引用答案 + 守卫状态；旁路 `/metrics` 记真实请求 p95，
`/eval` 读四配置 Recall@5 摘要。完整图与接口表见 [README.md](README.md)。

离线侧：golden_set.json → runner 四配置评测 → report 渲染对比表 →
ci_gate 与基线比较。报告数字全部来自离线侧，在线服务不参与"自评"。

## 4. 三个最难的点

1. **指标分母与方向**。Recall@k 的分母是标注片段数，Context Precision 的分母才是 k；
   MRR 只取首个命中位置。CI 门禁里质量的 delta 是"基线 - 当前"，延迟反过来。
   这些写反一个，报告就会得出完全相反的结论。
2. **测试集泄漏**。用同一批 case 调参再报最终数字，分数会虚高。
   正确做法是 dev/holdout 按 case_id 确定性划分，holdout 只报一次。
   本仓库的 100 条明确标注为教学样例，就是为了不冒充真实业务数据。
3. **诚实面对负收益**。本次实跑里 hybrid+rerank 的 Recall@5 是 0.900，
   低于其它三配置的 0.950；重排用的实词覆盖率让短小的归档片段占优。
   如果把文档示意的"rerank 0.91"抄进报告，看起来漂亮，但那是造假。

## 5. 数据（本地实跑，非真实业务指标）

```text
配置              Recall@5  MRR@10  Context Prec.  Faithfulness  p95
bm25_only         0.950     0.547   0.190          1.000         3.6ms
dense_only        0.950     0.424   0.190          1.000         3.1ms
hybrid            0.950     0.530   0.190          1.000         5.3ms
hybrid_rerank     0.900     0.509   0.180          1.000         6.1ms
```

- 四配置共用同一语料、同一生成器、同一 100 条教学样例，只换检索排序；
- 门禁示例把 hybrid_rerank 当当前、bm25_only 当基线，判定为回归（exit_code=1）；
- 逐案 recall 分布里每配置都有 5 条 0 值长尾，优化线索在那 5 条上。
- 完整表格与口径说明见 [REPORT.md](REPORT.md)，p95 为本地单机教学测量。

## 6. 面试叙事（30 秒版）

> 我把 RAG 从"能跑"做成了"能证明有效"：先建 100 条带来源标注的 golden set，
> 定义检索侧 Recall/MRR/Context Precision/Recall 与生成侧 Faithfulness/Answer Relevance，
> 再用同一套查询跑 BM25、伪稠密、混合、混合+重排四种配置做消融。
> 结果重排在短文档噪声下反而降了 5 个点，所以我按场景分流而不是一律上最贵配置。
> 最后用阈值比较做 CI 回归，质量下降或延迟上升超容差就退出码 1。
> 和"只会跑 Demo"的区别是：**我交付的是可复算的数字、可归因的消融和可拦退化的护栏。**

## 7. 边界与下一步

1. 本项目没有真实向量库、真实 Rerank 模型、真实业务文档；数字只代表教学语料。
2. golden set 用真实难例替换、dev/holdout 划分与指标重标定是上线前的必做项。
3. 第二阶段到此收口。第 13 周进入 Agent：`RAGService.query()` 会成为一个工具，
   本周的评测集是每次编排改动的回归基线；工具调用、规划与记忆是下一阶段任务。
